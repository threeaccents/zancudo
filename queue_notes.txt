Fqueue review notes
===================

Good: length-prefixed append-only log is simple. BufferTooSmall does not
advance offset, so it is retry-safe. RecordTooLarge is checked before any
work. errdefer close in init.


1. Head not persisted
   offset only lives in memory. On restart, init sets end = file length and
   offset = 0, so every already-consumed record is delivered again.
   Decide the goal:
   - survive restart: the head position must live on disk too
   - only spill RAM: truncate the file on open

2. Torn tail
   A crash mid-enqueue leaves a length prefix that promises N bytes, but the
   file holds fewer. init trusts file.length, so the last dequeue hits
   EndOfStream forever and the queue is wedged. Opening needs a way to
   detect a bad tail. Also no fsync: "written" does not mean "on disk".

3. Read amplification in dequeue (Fqueue.zig:49-50)
   Each call builds a new reader with a 64KB buffer. The first fill reads as
   much as fits, so a 20-byte record can cost a 64KB read, and the next call
   re-reads the same region. Reading exactly the 2-byte header, then exactly
   the payload, is enough.

4. Extra copy in enqueue (Fqueue.zig:31-34)
   The whole record is copied into a 64KB stack buffer just to prepend 2
   bytes. A vectored write (header + record) avoids the copy. Both enqueue
   and dequeue put 64KB on the stack per call.

5. dead_bytes always equals offset
   Both start at 0 and grow by the same amount. One is redundant until
   compaction gives them different meanings.

6. Dequeue happens before ack (MQTT spec)
   For QoS 1/2 the server must keep the message until it is fully
   acknowledged (PUBACK, or PUBCOMP for QoS 2). After dequeue the message
   lives only in the in-memory inflight list, so a crash before the ack
   loses it. A peek / commit split fits the spec better.

7. u16 length cap
   Fine today because in_buf is 16KB (Conn.zig:21). Breaks if the max
   packet size is raised later; MQTT allows up to ~256MB.


Truncation options
------------------
ftruncate only cuts from the end, never the front.

- Truncate when empty (offset == end): reset to 0. This is the commented
  line. Cheapest, and covers the common case where a client reconnects and
  drains everything.

- Compact once dead_bytes passes a threshold: copy [offset, end) to a new
  file, fsync, rename over the old one. Cost is copying the live bytes;
  rename keeps it crash-safe. This is the "start a new file" plan.

- Segments: roll to a new file every N bytes, delete a segment once the
  head passes its end. Nothing is ever copied. Kafka and NATS work this way.

- Linux fallocate(PUNCH_HOLE): frees the disk blocks of the consumed prefix
  in place. Offsets stay valid, nothing is copied, but the file's apparent
  size keeps growing.

Truncate-on-empty plus threshold compaction is enough for per-client
offline queues. Compaction only matters for a slow client that never fully
drains.


Open question
-------------
One file per offline session? Then every offline client holds an open fd;
10k offline clients means 10k fds and the ulimit gets hit. Opening files
lazily avoids that.
